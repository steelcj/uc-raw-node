## Departures from v0.1.8

Kept up to date as the work goes; each one is a candidate for v0.1.9.

- **Contract input as extra vars.** The design gives the command as `-e @raw-node-input.yml`, but `load_input.yml` read a file from `raw_node_input_file`, whose default was `{{ playbook_dir }}/raw-node-input.yml`, a path inside the repository. Following the design, `load_input.yml` now collects the five fields from extra vars, and reads a file only when `raw_node_input_file` is set explicitly. The default was removed, since it invited keeping contract input in the repository. Extra vars cannot be listed, so the "unknown fields" warning is only given for file input.
- **`raw_node_input_*` per field.** The design says `load_input.yml` copies each checked field into a `raw_node_input_*` variable. The existing code sets `raw_node_input` (a mapping, which is in the prefix) and `raw_node_hostname`, and both already work, so they were kept and no per-field variables were added. Nothing reads the other fields yet, since the payload is a placeholder.
- **`raw_node_strategy`.** The prefix table names `raw_node_strategy` as set by `resolve_platform.yml`; the existing name is `raw_node_delivery_strategy`, which works and was kept.
- **Output path defaults.** The design gives `{{ playbook_dir }}/records` and so on; per the known gap default they are built from `raw_node_root` instead.
- **`updated` in the attempt record.** The design lists hostname, platform key, strategy, transport, start time and state. The record also carries `updated`, the time of the last state change, which is what Phase 7 timings and an operator reading a stale `in_progress` record need.
- **Working variables in `prepare_paths.yml`.** The prefix table gives `prepare_paths.yml` only the expanded path names. Its intermediate values (repository root, resolved secrets path, ignore checks) use `raw_node_paths_*`, which the table does not list.
- **Directory modes.** The design does not give modes for the per-hostname records, reports and logs directories; they are created 0700. Records and reports are written 0644, logs and secrets 0600.
- **Transport output for the controller.** The prefix table has no name for what a transport hands back to the generic controller. `address.yml` sets `raw_node_transport_address`, next to the existing `raw_node_transport_result`, rather than an `raw_node_incus_*` name the controller would have to know.
- **`raw_node_destroy_standalone`.** A new switch, set by `destroy.yml`, so the transport's teardown can tell a build run from a standalone teardown (see the known gaps). It defaults to the safe side: an unset switch only deletes what the current run launched.

## Known gap defaults: outcomes

- **Paths when playbooks run from `tests/`.** Applied as given: `raw_node_root: "{{ playbook_dir }}"` in `vars/defaults.yml`, every repository-relative path built from it, `raw_node_root: "{{ playbook_dir }}/.."` in `tests/vars/output.yml`, and test playbooks include `../tasks/<file>.yml` and load `../vars/defaults.yml`. Works. `raw_node_root` also turned out to be the natural place to anchor relative output paths and to run `git rev-parse` from, which let `tests/prepare_paths.yml` point it at a throwaway repository.
- **Role search path for tests.** Applied as given: `roles_path = ./roles` kept in `ansible.cfg`; tests are run from the repository root.
- **Ownership check in standalone teardown.** Applied, with one change. The marker keys (`user.uc-raw-node.created=true`, `user.uc-raw-node.hostname=<hostname>`) are set at launch and required before any delete. The in-run check as given in the kickoff ("keep the in-run check" based on `raw_node_transport_result`) is not safe on its own: `raw_node_transport_result` is only set at the end of the transport, so in a build run that fails before then (in `payload.yml`, or when the transport refuses an existing instance) the rescue path would fall back to the marker alone, and would delete an earlier, possibly confirmed, node with the same hostname. The in-run check therefore uses facts the transport sets at its start and just before launch (`raw_node_incus_launched`, `raw_node_incus_adopted`): in a build run only an instance this run launched is deleted, and if this run launched nothing, teardown does nothing. The standalone `destroy.yml` says so with `raw_node_destroy_standalone: true` and relies on the marker alone. This stays within the default (marker on the platform, in-run check kept) rather than inventing a new design, but it is a change to the default and needs your confirmation.
- **Steps not yet buildable.** See Phase 4.
- **Failure record fields.** The design lists what the record holds but not the field names. They are `hostname`, `time`, `attempt` (platform key, strategy, transport, start time), `platform` (the resolved registry entry), `failed_task`, `reason`, `detail`, `clause`, `action`, and `teardown_error` when teardown fails. `clause` is "unknown" until the validator exists, and "none checked: no report was received" for `no_report`.
- **Platform error text in `teardown_error`.** The record keeps the teardown command's standard error, trimmed to 300 characters, because without it a quarantined node's record says only "non-zero return code". Teardown commands carry no payload or contract values; the rule against raw output applies to `no_log` tasks.
- **Attempt state when nothing was built.** When a build fails before the transport launched anything (the placeholders, or a refused existing instance), teardown has nothing to delete and succeeds, so the state becomes `destroyed` although nothing existed. The design has no state for "failed, nothing to clean up"; see open questions.
- **How `wait_phone_home.yml` finds `address.yml`.** It checks for `roles/raw_node_transport_<name>/tasks/address.yml` under `raw_node_root`, which assumes transports live in the repository's `roles/`. That holds until roles are packaged as a collection.
- **`destroy.yml` when record and `-e target_platform` disagree.** The design does not say which wins. `destroy.yml` stops and asks the operator to drop `-e target_platform`, rather than guessing.
- **`destroy.yml` runs `prepare_paths.yml`.** It needs the expanded paths and the same secrets checks, but `prepare_paths.yml` also creates the per-hostname directories, so a `destroy.yml` that stops early (no platform, or a refusal) leaves empty directories under records, reports, logs and the secrets path for that hostname. Harmless, but splitting the checks from the creation in `prepare_paths.yml` would avoid it.

## Found that the design does not cover

- **Several attempts for one hostname.** `write_attempt.yml` overwrites `attempt.yml`, but `failure.yml`, `confirmation.yml` and `report.yml` from an earlier attempt stay, so a successful build after a failed one leaves a stale `failure.yml` next to a `confirmed` attempt. The records layout holds one attempt per hostname; whether to clear, archive or number earlier attempts is not decided. The scenario runners clear the records between scenarios.
- **The validator's input from the confirmation.** The design says records are written from the resolved platform and the node's own report, never from the contract input, but the confirmation's `user` has to come from somewhere, and no report carries it yet. `write_confirmation.yml` takes `initial_username` from the input, the one public field.
- **How a step marks a reason code.** `no_report` is the only reason code the design names. `wait_phone_home.yml` signals it with `raw_node_report_status: no_report` and `handle_failure.yml` reads that; a general mechanism (for example a `raw_node_failure_code` beside `raw_node_failure_reason`) will be needed once the validator names clauses.
- **Test wrappers and `vars_files` precedence.** A test cannot wrap `build.yml` with `import_playbook` and override its `vars_files` with play vars. The wrappers use a first play with `set_fact`, which outranks `vars_files` in the imported play. This is worth a line in the design next to "Defaults after the move".
- **`fail_msg` is templated even when an assert passes** (ansible-core 2.21), so a message that reads a field which only exists on failure must guard it with `default`. Found in `prepare_paths.yml`.
- **`git` as a requirement.** The repository check needs `git` on the controller host. Without it, or outside a checkout, every path counts as outside the repository, with a note.

## Open questions

- **In-run teardown rule.** Do you accept the stronger in-run check (only delete what this run launched; do nothing if it launched nothing), with `raw_node_destroy_standalone` as the switch for `destroy.yml`? See the known gap outcomes.
- **Attempt state when nothing was built.** A build that fails before anything was created ends `destroyed`. Should there be a distinct outcome, for example leaving the state at `failed` when teardown had nothing to do?
- **An adopted instance in a failed build** is now quarantined (teardown refuses it), where the old code printed a note and carried on. Is quarantine right for `raw_node_incus_allow_existing=true` runs?
- **Contract input from a file.** Keep `raw_node_input_file` as an explicit alternative to extra vars, or drop it once nothing uses it? Only the tests use it today.
- **Stale records from earlier attempts** (see above): clear, archive or keep?
- **`raw_node_report_timeout` as a role-default fallback.** The Incus transport's `raw_node_incus_address_timeout` defaults to the controller's `raw_node_report_timeout`. Is it acceptable for a transport default to read a controller variable, or should `wait_phone_home.yml` pass the timeout explicitly?
